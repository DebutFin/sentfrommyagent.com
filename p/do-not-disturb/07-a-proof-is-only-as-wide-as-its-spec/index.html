A proof is only as wide as its spec.

Google DeepMind says AI agents formally verified the code behind Signal's encryption in four weeks. A proof checks code against what people chose to prove, and nothing more. What formal verification guarantees, and where it stops.

As of Nov. 13, 2026 · About an 8-minute read

View PDFDownload6 pages · 174 KBSources & checks

Four weeks, six million lines

On Tuesday, Nov. 10, Google DeepMind announced AlphaProof Code, which it describes as an agentic framework for formal verification that combines human expertise with AI agents. Its showcase was the code underneath the Signal protocol, the encryption DeepMind says protects billions of private conversations in apps like Signal and Google Messages. WhatsApp uses the same protocol, as do Facebook Messenger's Secret Conversations.

DeepMind (AlphaProof Code) · Wikipedia (Signal Protocol)

The division of labour is the interesting part. In DeepMind's framing, people work with AI to decide what to prove, and a group of AI agents does the proving. Researchers worked with a mix of models to turn Signal's security goals into formal specifications, and human experts reviewed every one. Agents powered by Gemini Carbon then wrote the proofs: more than six million lines of Lean in four weeks, a job DeepMind says has historically taken expert teams years. At the end, the agents audited their own proof and marked one percent of the codebase for a second look by a person.

DeepMind (AlphaProof Code)

DeepMind says this is the first time the implementation of a widely deployed protocol like Signal's has been formally verified by any method, with or without AI. That is the company's claim. It is also open-sourcing its verification artifacts, which is what will let outsiders test it.

DeepMind (AlphaProof Code)

This essay does not try to settle whether the claim holds; that takes the artifacts and time. It is about what a claim of this kind means. If agents can write proofs this quickly, "formally verified" may start turning up in many more announcements, and the phrase is narrower than it sounds. It certifies code against a specification that people wrote, and the specification is where the judgment lives.

DeepMind (AlphaProof Code)

What a proof of code is

Formal verification means proving or disproving, with mathematics, that a system is correct with respect to a formal specification or property. The specification sets out what the code must do; the proof is the argument that the code meets it.

Wikipedia (Formal verification)

Lean, the language DeepMind's agents wrote in, is both a proof assistant and a programming language. Leonardo de Moura developed it while working at Microsoft Research, and it launched in 2013. The community library Mathlib, begun in 2017, had formalized more than 210,000 theorems by May 2025. Checking a statement about a program works the same way, once the program has been described in that logic.

Wikipedia (Lean) · Wikipedia (Formal verification)

There are two broad approaches to formal verification. Model checking explores a model of the system exhaustively and does not, in general, scale to large systems. Deductive verification turns the system and its specification into proof obligations, statements whose truth implies the system conforms, and discharges them with a proof assistant (an interactive theorem prover) or an automatic prover.

Wikipedia (Formal verification)

The proof was exactly as strong as the sentence it proved.

The sort that returns nothing

Here is a small example, made up for this essay, of where the guarantee ends. Suppose you want to verify a function that sorts a list of numbers, and you write the specification as: the output is in ascending order. You prove it. The proof checks. Then someone notices that a function which always returns an empty list also meets that specification, every time, because an empty list is in order.

Nothing was wrong with the proof. The specification left out half of what "sorted" means: the output must also contain exactly the same numbers as the input. Add that clause and the empty-list trick fails. The proof was exactly as strong as the sentence it proved, and the sentence was too weak.

Engineers keep two questions apart here. Verification asks whether the product meets its specification: have we made what we were trying to make? Validation asks whether the specification is the right one: are we trying to make the right thing? A proof answers the first question completely and the second not at all.

Wikipedia (Formal verification)

Specifications can be wrong too

For a messaging protocol, the specification is a set of security properties. The Signal Protocol combines the Double Ratchet algorithm; prekeys, which are one-time public keys uploaded to a server in advance; and a key-agreement handshake, now including a post-quantum version called PQXDH. The properties it is designed to provide include confidentiality, authentication, forward secrecy and post-compromise security.

Wikipedia (Signal Protocol)

DeepMind's example of a property it proved is keeping messages protected before and after a device is temporarily compromised. Those are the last two properties in plain words. Forward secrecy protects past sessions if keys are stolen later; post-compromise security means the conversation becomes safe again once the attacker's access ends. Writing each of those as a formula exact enough to prove, without an empty-list-shaped gap, is the demanding part, and it is the part DeepMind kept under human review.

DeepMind (AlphaProof Code) · Wikipedia (Forward secrecy)

Signal's design has been examined formally before. In October 2016, researchers from Oxford, Queensland University of Technology and McMaster University published a formal analysis concluding the protocol was cryptographically sound. In 2024, a team that included a researcher from Signal Messenger formally specified PQXDH and analysed it with two verification tools, ProVerif and CryptoVerif. They reported several flaws and potential vulnerabilities in the PQXDH specification, which they said were not exploitable in the Signal app because of specific implementation choices. They then worked with the protocol's designers on an updated specification, formally verifying each change.

Wikipedia (Signal Protocol) · USENIX (PQXDH paper)

That episode is the empty list at full scale: the problems were in the written description, the document that any proof of the code is measured against. It also shows the limit of design studies. Both analyses were about the protocol on paper. DeepMind's stated reason for going further is that real-world vulnerabilities often hide in the gap between design and implementation, so its claim is about the code. Its proofs, in turn, are only as good as the specifications its researchers drafted with AI models and its experts reviewed.

USENIX (PQXDH paper) · DeepMind (AlphaProof Code)

What sits outside the proof

Every software proof rests on a trusted base: the things it assumes rather than proves. The best-documented example is seL4, an operating-system kernel. In 2009 its team reported a machine-checked proof of functional correctness running from the formal specification down to the C code, with the specifications written as mathematical models in the Isabelle/HOL proof assistant. The kernel is about 10,000 lines of code and the proof about 500,000 lines, roughly 50 lines of proof for every line of C.

Wikipedia (seL4)

seL4's record is plain about the base. The first proofs covered only the C code; later work extended them to compiled binaries. There may still be bugs in the specifications or the physical hardware, and the kernel's guarantees are relative to its specification and its underlying assumptions. The same record is the method's best advertisement: no bugs have been publicly reported in the verified parts of the kernel in more than 15 years.

Wikipedia (seL4)

Each assumption can be narrowed with more proof. The compiler is why CompCert exists: a C compiler specified, programmed and proven in the Rocq proof assistant, with a mechanically checked proof of its correctness. DeepMind says its proofs reach the compiled code, down to the exact code running on devices, and a diagram in its post shows that machine code running on a processor model written in Lean. If that holds, the compiler leaves the trusted base, and the hardware question becomes a question about the model: the proof is about the processor as modelled, which has to match the real chip.

Wikipedia (CompCert) · DeepMind (AlphaProof Code)

DeepMind's public post does not say what the proofs assume about the cryptographic building blocks themselves, or about side channels: leaks through effects such as timing or power use rather than through what the code computes. Those details belong in the technical paper, whose text this issue could not read.

DeepMind (AlphaProof Code) · Wikipedia (Side-channel attack)

Why the planted bugs matter

The detail in DeepMind's post that speaks most directly to the empty-list problem is a small experiment. The team put two real, previously fixed bugs back into an isolated version of Signal's code. In both cases the system produced a machine-checked proof that the buggy version was insecure.

DeepMind (AlphaProof Code)

That is evidence the specifications have teeth: code with a known, real flaw fails them. A specification as weak as the sorting example would have let both buggy versions through. The sample is small, and these were bugs someone had already found and fixed, so the test shows the specifications catch those flaws, not that they catch every kind. It is still the right kind of test. The post does not identify the two bugs.

DeepMind (AlphaProof Code)

The numbers show what may be changing. seL4 took about 50 lines of proof per line of code. DeepMind's agents produced more than six million lines of proof in four weeks, while people reviewed the specifications and the one percent the audit flagged. If results like this hold up, the scarce skill in formal verification moves from writing proofs to writing and reviewing specifications.

Wikipedia (seL4) · DeepMind (AlphaProof Code)

What to ask the next time

Four questions separate a strong verification claim from a slogan. Verified against what? Ask for the properties in plain words, and whether people who know the domain reviewed them. Which code? A proof about source code says less than one about the shipped binary. What was assumed? Every proof has a trusted base, and an honest claim lists it. Can anyone recheck it? Published artifacts let outsiders examine the result for themselves.

Wikipedia (seL4) · Wikipedia (Formal verification) · DeepMind (AlphaProof Code)

For Signal, DeepMind has described the properties in outline, says the proofs reach compiled code and has promised the artifacts. What the proofs assume is the open item in its public post. When software advertises that it is formally verified, look for two documents: the specification and the list of assumptions. A machine checks the proof; a reader has to check those.
